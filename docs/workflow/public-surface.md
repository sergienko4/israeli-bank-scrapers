# Public API surface gate

`npm run lint:public-surface` asserts that the package's exported API matches
the snapshot committed at `api-surface.d.ts`.

## Why this gate exists

The pre-PR contract asked every author to certify "public API byte-identical at
`lib/index.cjs`", and gave this as the verification:

```powershell
$pre  = git show "main:lib/index.cjs"
$post = Get-Content "lib\index.cjs"
$diff = Compare-Object $pre $post
if ($diff) { Write-Error "lib/index.cjs drift detected" }
```

That command cannot work in this repository, and the way it fails is the
dangerous part:

1. `lib/` is gitignored and has never been tracked, so `git show` exits 128
   and writes nothing to `$pre`.
2. `Compare-Object` refuses a null reference object, so `$diff` is never
   assigned.
3. `if ($diff)` is therefore false, so the guard that was supposed to raise
   the alarm passes.

Both `git` and `Compare-Object` do print errors, so this is not silent in a
terminal. But no comparison ever happens, and the only signal the contract
actually consumed — the `if ($diff)` guard — reports success. Any caller that
checked the guard rather than watching stderr recorded a false green, which is
worse than a missing gate: the compliance table logged a verification that had
compared nothing. Reproduce the first step:

```bash
git cat-file -e origin/main:lib/index.cjs   # fatal: ... but not in 'origin/main'
```

The second flaw is *what* it compared. `lib/index.cjs` is the bundled
implementation. Renaming an internal module, reordering an import, or a change
in treeshaking output all move its bytes while the exported API is untouched —
so the check would have reported drift a reviewer could not act on, had it ever
run. `scripts/decoupling-metrics/diff.mjs` already labels its own hash of that
same file an "implementation bundle, not a declaration-level API diff". This
gate is the declaration-level diff that sentence implies.

## What it checks

`lib/index.d.ts` is the public surface: every exported value, type and
signature, and nothing internal. `tsup` generates it from `src/index.ts` under
`dts: true`. The gate:

1. Requires the build to exist. A missing `lib/index.d.ts` or `lib/index.d.cts`
   exits **2** — the condition the old check swallowed is now the loudest one.
2. Requires `lib/index.d.ts` and `lib/index.d.cts` to be identical. They are
   generated byte-for-byte the same today; a divergence would mean `require()`
   and `import` consumers see different APIs, which no single snapshot could
   represent honestly.
3. Compares `lib/index.d.ts` against `api-surface.d.ts` and prints a unified
   diff on mismatch.

Because the snapshot is a tracked `.ts` file, `origin/main` genuinely holds a
baseline, and an API change shows up in the PR diff in a form a reviewer can
read — which is the property the original check was reaching for.

## Updating the snapshot

A surface change is legitimate often enough (a new export, a widened type).
When it is intended:

```bash
npm run build
npm run api:update      # rewrites api-surface.d.ts from the build
git add api-surface.d.ts
```

Commit the snapshot **with** the change that caused it. Reviewing that diff is
the point: it is the moment the API change becomes visible.

## Running it

```bash
npm run build                 # the surface is a build artifact
npm run lint:public-surface   # verify
npm run api:update            # accept a change
```

Exit codes: `0` surface matches, `1` surface drifted, `2` cannot verify (build
or snapshot missing). `2` is never a pass.

## Where it runs

| Surface | Entry point |
| --- | --- |
| Pre-commit | Folded into the `build` gate in `.husky/pre-commit`, immediately after `tsup` produces `lib/`. Gates run in parallel, so it shares the gate that guarantees the build exists rather than racing it. |
| CI | The `Check public API surface` step in `.github/actions/build-package/action.yml`, alongside the existing output checks and `publint`. |

The CI step only runs if the `build` job runs. That job used to be gated solely
on `full_suite` (`src` or `critical_deps`), which meant a change to
`api-surface.d.ts`, to the checker, or to the build action itself — changes
whose entire purpose is this gate — would skip it. `detect-changes.sh` now emits
a separate `public_surface` flag for those paths and the `build` job gates on
either. `full_suite` was deliberately left alone: its definition is pinned by
`CriticalDepsFullSuiteGate.test.ts`, and widening it would have pulled the whole
heavy suite along with it.

`--update` refuses to run when `CI` is set. Regenerating a baseline is an
authoring step that a human reviews; a CI job doing it would bless drift instead
of reporting it.

## Known limitations

This detects **declaration-level** drift. It cannot detect a behavioural change
behind an unchanged signature — a function that keeps its type but starts
returning different values passes this gate. That class belongs to tests and
review.

Three further boundaries are worth stating plainly, because each is a way to
read more into a green result than it earns:

- **It compares the build to the reviewed snapshot, not to `main`.** Exit `0`
  means "the surface I built matches the snapshot in this commit". A deliberate
  API change plus `npm run api:update` is also exit `0` — correctly so. To ask
  the different question "did the API change at all", diff the snapshot itself:
  `git diff origin/main...HEAD -- api-surface.d.ts`. That diff is the review
  artifact; the gate only guarantees it cannot be out of date.
- **It reads `lib/`, so it is only as fresh as your last build.** Run it
  standalone after editing `src/index.ts` without rebuilding and it will compare
  a stale declaration and pass. Always `npm run build` first — the pre-commit
  hook and the CI action both do, which is why they are the authoritative
  invocations.
- **It does not cover the package entrypoints.** `main`, `module`, `types` and
  the conditional `exports` map in `package.json` decide what a consumer can
  actually import. Redirecting one of those changes the usable API while the
  declarations stay identical. `publint` (`npm run check-exports`) is the check
  for that, and it runs in the same CI job.

It also makes no claim about the bundle being byte-identical. That was never
the right question for a package whose build output legitimately churns.
